# UNO Q motion games: architecture and how to make a new one

There are three App Lab apps in this repo. They share the hardware and most of the plumbing:

| Game | Folder | Controller | Gestures (DEFAULT_LABELS) | Multiplayer |
|---|---|---|---|---|
| Ardu Kart | `ardu-kart/` | wheel: tilt steers (roll, fused with the accelerometer) | `idle, accelerate, brake, use_item, change_camera` | up to 20 browsers on **one** board |
| Ardu Fishing | `ardu-fishing/` | rod: gyro yaw about gravity aims (tilt still supported) | `idle, cast, reel, unhook` | tournament **between boards** (join by IP) |
| Ardu Snowball | `ardu-snowball/` | hand controller: tilt turns the player | `idle, scoop, pack, throw, run` | 3 v 3 **between boards** (join by IP) |

Hardware: an Arduino UNO Q with a Modulino Movement (IMU), a Modulino Buttons (A/B/C and their LEDs) and a Modulino Pixels (8 RGB LEDs), plus the board's 8x13 LED matrix.

Sibling skills (use them, don't copy them):
- `arduino-unoq-applab`: general UNO Q, App Lab, Bridge and brick reference.
- `modulino-imu-aim`: the aim/steer filter (`_sample`, calibration, the yaw and tilt modes).
- `edge-impulse-motion-gestures`: recording, training and mapping gestures (Motion Lab, Edge Impulse).
- `motion-game-devtools`: simulator, headless tests, and deploying to `my-unoq.local`.

## 1. Layout of one game

```
ardu-<game>/
├── app.yaml            name, icon, description; bricks arduino:web_ui + arduino:motion_detection
├── python/
│   ├── main.py         game server: lobby/match relay, records, LED-matrix state, 20 Hz tick
│   ├── controller.py   MotionHub: Modulino <-> browsers, engines, ownership, Motion Lab, EI API proxy
│   ├── brick_engine.py BrickEngine: gesture inference with the Motion detection brick
│   └── model_installer.py  installs an EI Arduino library zip into sketch/
├── sketch/
│   ├── sketch.ino      Modulinos, Bridge, LED matrix, Pixels, optional on-MCU EI model
│   ├── led_frames.h    pure matrix renderer + parseLedState() (desktop-testable)
│   ├── model_config.h  generated by model_installer.py (<PREFIX>_HAS_MODEL 0/1)
│   └── sketch.yaml     arduino:zephyr profile, Arduino_Modulino (0.7.0) + pinned deps
└── assets/
    ├── index.html      game page (loads libs/socket.io.min.js, then js/main.js as a module)
    ├── train.html      Motion Lab (js/train.js)
    ├── js/             main.js, net.js, input.js, motion.js, ui.js, hud.js, audio.js, util.js, game files
    ├── libs/           socket.io.min.js, three.bundle.js (esbuild bundle, see devtools/vendor-entry*.js)
    └── img/edge-impulse-logo.png
```

Prefixes are per game: Python env vars, sketch macros and localStorage keys use `ARDUKART_`/`ardukart.`, `ARDUFISH_`/`ardufish.` and `ARDUSNOW_`/`ardusnow.`. The simulator env vars stay `ARDUKART_SIM_*` in every game.

## 2. Data flow

```
sketch.ino ──Bridge.notify──▶ controller.MotionHub ──ui.send_message(room="motion")──▶ browser MotionController (motion.js)
  "imu" "ml" "btn" "hw"         on_imu/on_ml/on_btn/on_hw        "imu" "ml" "btn" "hw" "motion_owner"
                                                                                │
sketch.ino ◀──Bridge.notify── controller / main.py ◀──Socket.IO── browser ──────┘
  "led_state" "pix"/"rev"        on_pix/on_rev, on_leds,           "pix" (or "rev" in Kart), "ctl_leds",
  "btn_leds" "gesture"           push_led_state()                  "solo_status", "motion_claim", ...
  "ml_engine"
```

| Message | Direction | Payload | Rate / notes |
|---|---|---|---|
| `imu` | MCU → Py | `ax, ay, az` (g), `gx, gy, gz` (deg/s) | every sample, 62.5 Hz (`<PREFIX>_SAMPLE_US 16000`) or the model's `EI_CLASSIFIER_INTERVAL_MS` |
| `imu` | Py → room `motion` | `{s: [[6 values], ...], i: interval_ms}` | batched, `IMU_BATCH = 2` (about 31 msg/s) |
| `ml` | MCU → Py → room | `probs_csv, dsp_ms, nn_ms` → `{labels, p, dsp, nn, t, src}` | `INFER_STRIDE_MS = 250` (4 Hz); brick `STRIDE_MS = 250` |
| `btn` | MCU → Py → room | `index, pressed` → `{i, p}` | edges only, polled every 15 ms |
| `hw` | MCU → Py | `"v=2;mv=1;bt=1;px=1;interval=16.00;model=0[;name=;project=;deploy=;window=;axes=;labels=a\|b]"` | heartbeat every 2 s; `BOARD_TIMEOUT_S = 5` |
| `hw` | Py → room | `status_payload()`: `online, hw, installed, restartNeeded, job, owner, ownerKind, ownerVisible, engine` | when something changes |
| `pix` / `rev` | browser → Py → MCU | Fishing/Snowball `{mode, value}`; Kart `{speed, flags}` | owner only; `flush_pix`/`flush_rev` caps at 25 Hz (`PIX_MIN_INTERVAL_S = 0.04`), repeats at most every 0.5 s |
| `ctl_leds` → `btn_leds` | browser → Py → MCU | `{mask}` bits 0/1/2 = A/B/C | owner only, sent when the mask changes |
| `led_state` | Py → MCU | compact string, such as `fish:173:4:3` | `push_led_state()` in the 20 Hz tick, resent at least every `LED_PUSH_S = 1.0`; the MCU drops to the dim idle frame after `LED_STATE_TIMEOUT = 3500` ms |
| `gesture` | Py → MCU | `cls, label, pct` | brick results only, for the matrix icon and Pixels flash (same 0.7 threshold, 0.9 s per class) |
| `ml_engine` | Py → MCU | `1` = the MCU model drives, `0` = the brick drives | resent with every heartbeat (it survives an MCU reset) |

Full message lists, including the Motion Lab and multiplayer ones, are in `references/protocol.md`.

Key conventions:
- The sketch registers handlers with `Bridge.provide_safe(...)`, so they run in the loop thread. Python registers `bridge.provide("imu"|"ml"|"btn"|"hw", ...)` in `MotionHub.register()`, inside a `try` so that the game still runs without the router.
- The browser `Net.request(name)` emits `name` and resolves with the WebUI brick's `<name>_response`. `joinRoom()` emits `enter_room`. Rooms do not survive a reconnect, so re-join in the `connect` handler.
- Every Modulino is optional and hot-pluggable: `probeModulinos()` retries every `PROBE_INTERVAL = 2500` ms.

## 3. Gesture engines

`MotionHub._pick_engine()` in `python/controller.py`:

| `engine_pref` | Result |
|---|---|
| `auto` (default) | `mcu` if the heartbeat says `model=1` and the board is online, else `brick` if `BrickEngine.ready`, else `None` |
| `mcu` | `mcu` or `None` |
| `brick` | `brick` or `None` |

- **Brick** (`brick_engine.py`): `MotionDetection.get_model_info()` (retried every 10 s) sets up the window. `push()` resamples the IMU stream to the model rate in m/s² and deg/s. A worker calls `MotionDetection.infer_from_features()` every 250 ms, with a 1-slot queue that drops windows when it falls behind. You swap the model in App Lab without rebuilding the sketch.
- **MCU**: `model_installer.py` unpacks the EI Arduino library into `sketch/libraries/` and rewrites `model_config.h` and `sketch.yaml`. The sketch then runs `run_classifier` on a rolling window. `buildAxisMap()` maps `EI_CLASSIFIER_FUSION_AXES_STRING` onto the six channels. The new model needs an app restart (`restartNeeded`).
- The preference is saved in `<data>/motion.json` and changed with `motion_engine {engine}`. On the browser side it is `MotionController.setEngine()`, the "GESTURE ENGINE" selector in the motion screen of `ui.js`.
- `_refresh_engine()` runs on every heartbeat, on brick state changes and in `tick()` when the MCU goes stale. When the engine changes it clears `last_ml`, flushes the brick window, sends `ml_engine` and broadcasts `hw`.

## 4. Who owns the controller

There is one controller per board but there may be many tabs: App Lab opens a new tab on every Run, the Motion Lab is a tab, and in Kart LAN players use the same board. `MotionHub.owner/owner_kind/owner_visible` decide which tab drives.

| Message | From | Meaning |
|---|---|---|
| `motion_claim {force, focused, visible}` | game tab | take it if it is free or already ours, if `force` is set, or if `focused` and the current owner is the lab or not visible |
| `motion_claim {force: true, kind: 'lab'}` | Motion Lab (`train.js`) | the lab takes it when it opens or gets the focus |
| `motion_claim {release: true}` | owner | let go (the setting "off") |
| `motion_visible {visible}` | owner | sent on `visibilitychange` |
| `motion_owner {id, kind, visible}` | server → room | broadcast after every change, and after `forget(sid)` on disconnect |

Browser side (`motion.js`):
- `_autoClaim()` runs on `focus`, `visibilitychange`, status and owner events. `_startGame()` calls `motion.claim(false)`.
- `active` is true when the controller is online, the setting isn't `'off'`, and this tab owns it or nobody does. Only then do `poll()`, `_onMl` and `_onButton` act. Held buttons are cleared when the tab loses ownership.
- Python's `_may_drive(sid)` ignores `pix`, `rev` and `ctl_leds` from tabs that are not the owner.
- A tab that doesn't drive still shows the HUD with "WHEEL/ROD/CONTROLLER ON ANOTHER SCREEN" (or "... IN THE MOTION LAB") and a "USE THE ... HERE" button (`takeWheel` / `takeRod` / `takeController` → `claim(true)`).
- Old tabs that don't report `visible` count as hidden. A focused game tab never takes the controller from another LAN player's game that is on screen.

## 5. Browser game structure

See `references/browser-game.md` for details. In short:
- `main.js` has `class App`: `loadSettings()`, `_initRenderer()` (three.js and EffectComposer), `_initNet()`, `boot()` (loader steps, attract mode, `renderer.compile`, then `ui.reset('title')`) and `loop(now)` (`input.poll` → `ui.handle` or `game.update` → `world.update` → `motion.update()` → `_sendStatus()` → `render` → `_adaptResolution`). The app is exposed as `window.ardukart` / `window.ardufish` / `window.ardusnow` for tests.
- `input.js`: `Input.poll(dt)` merges the keyboard (`KEYMAP`), gamepads, touch (`#touch`) and `motion.poll()` into one `state`, plus a `menuQueue` of `ok/back/up/down/left/right`. The controller aims unless the keyboard, pad or touch is being used right now.
- `motion.js`: `MotionController`. It holds `ACTIONS`, `DEFAULT_LABELS`, `defaultAction(label)` (keyword regex), `EDGE` actions (fire once, `EDGE_COOLDOWN_MS`, re-armed when the class drops below 0.6 × threshold) and `HOLD_MS` actions (held for N ms per detection). It also builds the bottom-left `#motion-hud` with every class and its confidence.
- `ui.js`: a DOM menu stack (`show`, `back`, `reset`, `hide`) with spatial focus over `.nav`, driven by the keyboard, gamepad and Modulino buttons. Screens include title, main, settings, help, records, the motion screen and calibration, plus lobby screens.
- `hud.js`: in-match DOM overlay. `audio.js`: procedural Web Audio (no audio files), unlocked on the first pointer or key event.
- Settings live in `localStorage['<prefix>.settings']`, with `motion: {...defaultMotionSettings(), ...}`. `defaultMotionSettings()` returns `{enabled:'auto', sensitivity:0.5, deadzone:0.15, invert:false, threshold:0.7, map:{}, cal:null}`.
- Vendor libraries are not on a CDN. `assets/libs/three.bundle.js` is built with esbuild from `devtools/vendor-entry.js` (Kart), `vendor-entry-fishing.js` or `vendor-entry-snowball.js` (three r187 plus the postprocessing passes). Modules import it with `import * as THREE from '../libs/three.bundle.js'`. Socket.IO is a classic script, `libs/socket.io.min.js`.

## 6. Multiplayer

See `references/multiplayer.md`.
- **Kart, one board:** every browser connects to the same board. `lobby_join`, `lobby_settings`, `lobby_start` → `race_start {raceId, seed, track, cc, laps, startAt, grid, hostId, netHz}`. Each browser sends `state` for the karts it owns, and the server merges them into a `snapshot` in room `race` at `netHz` (20 Hz, or 10 Hz above `BIG_FIELD = 10` humans). `event` is relayed with `from` and `t` and is rate-limited.
- **Fishing tournament, between boards:** `Tourney` (`tourney.js`) opens a second `Net(hostUrl(addr))` to the host board. The WebUI brick accepts cross-origin sockets. `tourney_join/ready/start`, then `tourney_start {matchId, seed, startAt, durationMs, players}` goes to room `tourney`. Browsers send `tourney_score` (every 500 ms) and `tourney_catch`. The host broadcasts `tourney_scores` (≤ 4 Hz) and `tourney_results`. The motion controller and the LED matrix stay on the local board.
- **Snowball, between boards:** `Lan` (`lan.js`) joins rooms `lobby` and `match`. The host browser simulates the bots and owns the stars and the score, and another player takes over if it leaves.
- Synced start in all three: `Net.syncClock()` (the lowest-RTT of 4 `clock` pings, every 5 s) gives `net.now()`. The local start is `performance.now() + (startAt - net.now())`. A shared `seed` feeds `makeRng()` (mulberry32 in `util.js`), so every client builds the same world.

## 7. Records and the Motion Lab

- Records are kept by `RecordStore` in `main.py`: `<data>/records.json`, with an atomic `tmp` + `os.replace` write, debounced by `SAVE_DEBOUNCE_S`, a top-10 per list, and a corrupt file renamed to `.bad`. `resolve_data_dir()` tries `$<PREFIX>_DATA_DIR`, then `/app/data`, then `<app>/data`. Browsers also keep `localStorage['<prefix>.records']` for offline play. Messages: `record`, `get_records`, and a `records` broadcast.
- The Motion Lab is `assets/train.html` with `js/train.js`. The main menu links to it ("TRAIN YOUR MOTION CONTROLLER" → motion screen → "TRAIN YOUR GESTURES", which calls `window.open('train.html')`). It records on the board (`motion_record`, which is sample-accurate) and proxies Edge Impulse (`ei_project`, `ei_upload`, `ei_job` retrain/build, `model_upload`, `model_remove`). The API key is stored in `localStorage['ardukart.ei.key']`, shared by all three games. See `edge-impulse-motion-gestures`.

## 8. Board feedback conventions

| Output | Convention | Where |
|---|---|---|
| Button LEDs | Light the buttons that do something **now**: `game.buttonMask()` in a match (Fishing aim=A, wait=A+B, fight=B, unhook=C). Menus light all three; on the title screen A blinks (600 ms of every 1000 ms); the Motion Lab lights A. Kart lights all three outside the title screen | `motion.js update()` |
| Buttons in menus | A/B/C = `ok/back/next` (Kart: `ok/back/down`, and A/B/C start a quick race / GP / LAN on the main screen) | `_onButton` |
| Buttons in play | A fallback for every gesture: Kart A or C (hold) = gas, B = item. Fishing A = cast, B (hold) = reel, C = unhook. Snowball A = throw, B (hold) = run, C = scoop or pack | `_onButton`, `poll()` |
| Pixels | `game.pixels()` → `[mode, value]`. Fishing modes 0-7 (aim marker, waiting, bite strobe, tension bar, unhook progress, rainbow, snapped). Snowball modes 0-7 (ammo, carrying, frozen, hit, capture, star stolen, countdown). Kart `rev` shift lights (speed, flags racing/boost/drift/finished). A gesture flashes in its class colour (`CLASS_RGB`); otherwise there is an idle scanner | `sketch.ino renderPixels()` |
| LED matrix | Python decides with `get_led_state()`: `idle`, `lobby:n`, `count:N` (3..0), then the in-play state (`race:lap:laps:pos`, `fish:secs:fish:phase`, `play:secs:ammo:flags:my:their:snow%`), then `finish:...`. A detected gesture overlays an icon for 700 ms (`renderGesture`, chosen by `gestureIconFor(label)` with the same keywords as `defaultAction`) | `main.py`, `led_frames.h` |
| Browser → matrix | `solo_status {state, count, ...}` while playing (Kart every 0.25 s from `race.js _soloStatus`, Fishing every 0.5 s from `App._sendStatus`, Snowball from `game.js`), and `{state:'menu'}` every 3 s in menus. The newest non-menu status from the last `SOLO_STALE_MS = 4000` ms wins | `main.py get_led_state()` |

## 9. Start a new game from an existing one

Pick the closest base: **Fishing** for a solo or tournament game where each player has their own board, **Snowball** for real-time LAN with bots, **Kart** for many browsers on one board. The full checklist with commands is in `references/new-game-checklist.md`. In short:

1. Copy the folder: `cp -r ardu-fishing ardu-<game>`. Delete `data/`, `sketch/libraries/`, `sketch/build/` and `python/__pycache__/`, and add the first three to `.gitignore`.
2. `app.yaml`: set a new `name`, `icon` and `description`, and keep both bricks. Update the comment that lists the classes. Ports: the WebUI brick serves on 7000 (`WebUI(port=...)`, `<PREFIX>_PORT` locally), and only one app runs on a board at a time.
3. Rename the prefix everywhere: env vars (`ARDUFISH_` → `ARDUXXX_`), sketch macros (`ARDUFISH_HAS_MODEL`, `ARDUFISH_EI_HEADER`, `ARDUFISH_SAMPLE_US`, ...) in `sketch.ino` and `model_installer.py`, the `[Ardu Fishing]` log tags, `localStorage` keys, `window.ardufish` and the devtools that use it. Keep `ARDUKART_SIM_*` and `ardukart.ei.key`.
4. `sketch/sketch.yaml`: keep the `arduino:zephyr` profile and the pinned library versions, which must match `BASE_LIBRARIES` in `model_installer.py`. Reset `model_config.h` to `<PREFIX>_HAS_MODEL 0`.
5. Keep as they are (rename only): `controller.py`, `brick_engine.py`, `model_installer.py`, `net.js`, `util.js`, `train.html`/`train.js`, and the ownership and HUD code in `motion.js`.
6. Rewrite for the new game: `ACTIONS`, `DEFAULT_LABELS`, `defaultAction()`, `EDGE`, `HOLD_MS`, `poll()` and `_onButton()` in `motion.js`; `KEYMAP`, gamepad and touch handling in `input.js` and `#touch` in `index.html`; `game.pixels()`, `buttonMask()`, `wantedAction()`, `status()`; `led_frames.h` states, `parseLedState()` and `gestureIconFor()`; `onPix()` and `renderPixels()` in `sketch.ino`; `get_led_state()`, `on_solo_status()`, `RecordStore` and the lobby or match handlers in `main.py`; the help text and the motion screen in `ui.js`.
7. Keep the sketch's `isIdleLabel()` and `GESTURE_CONFIDENCE`, the Python `IDLE_RE` and the browser `defaultAction` keywords consistent with your class names.
8. Bundle three.js: add `devtools/vendor-entry-<game>.js` and run esbuild (the command is in the file header).
9. Add `devtools/run_<game>.sh` (copy `run_fishing.sh`: set `ARDUXXX_ASSETS`, `_DATA_DIR`, `_PORT`, `_APP_DIR` and `ARDUKART_SIM_LABELS`) plus a headless check. See `motion-game-devtools`.
10. Write `ardu-<game>/README.md` (play, train, buttons, LED matrix, Pixels, run on the board) and add the game to the TIP in the root `README.md`.

## 10. Design rules from playtesting

Each rule is backed by the code or the commit history:
- **3-minute matches** (`MATCH_MS = 180000` in Fishing and Snowball, `MATCH_SECONDS 180` in `led_frames.h`). Allow an env override for tests only (`ARDUFISH_MATCH_MS`).
- **Every action works without the model:** keyboard, gamepad and touch (`input.js`), plus Modulino buttons for every gesture. The HUD names the fallback: "NO MODEL · BUTTONS A B C" in Fishing and Snowball. In Kart it is "HOLD A OR C TO ACCELERATE", and with neither a model nor buttons the kart accelerates by itself (`autoGas`).
- **The HUD shows every class with its live confidence** and the threshold mark, bottom left. The class the game wants now glows (`wantedAction()`), and the panel goes stale after `ML_STALE_MS`.
- **Button LEDs light only the buttons that do something now.**
- **Use the model confidence as quality:** a cleaner cast lands closer and a cleaner throw flies further (`_gesture(label, action, p)`).
- **The tab you look at drives the controller.** Report visibility, take the controller from the Motion Lab or a hidden tab, never from another visible game, forget held buttons when the tab loses it, and show the HUD with "on another screen" plus a take-over button.
- **Clear the screen marker when hiding menus** (`ui.hide()` → `onScreen('')`). Otherwise results-screen CSS hides the HUD after Retry.
- **`replaceChildren()` prints a `null` child as "null"**, so `.filter(Boolean)` the children first (see `hud.js`). The `el()` helper already skips `null` and `false`.
- **Re-join rooms on every reconnect.** Resend LED state every second and `ml_engine` with every heartbeat, because both sides can restart.
- **Keep Python thin:** the board has 2 GB of RAM, so physics, bots and rendering run in the browser (`ardu-snowball/python/main.py` header). Validate and clamp every client value (`clean_name`, `as_int`, `rate_limited`), and only let scores go up.
- **Scale the network rate with the field size:** 10 Hz snapshots above 10 humans (Kart), and remote karts are interpolated.
- **Aim from the gyro when the accelerometer can't see the motion** (a yaw about gravity), and wrap the filtered tilt to ±180°. See `modulino-imu-aim`.
